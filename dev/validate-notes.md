## Interfejs (dla T6 / T7 / T8)
- Model: `pack.proposalTools()` -> `check_proposal`, `submit_proposal` (ten sam schemat strict `PROPOSAL_SCHEMA`; opis pól raz, w opisie `submit_proposal` = `PROPOSAL_GUIDE`). `pack.runProposalTool(name, input, { doc, options: { rank, profile } })` -> `{ ok, proposalId?, summary?, errors?, warnings, info?, autoFixed?, budget, layer? }`. Błąd = `{ code, path?, opId?, message, hint, suggest? }`. Udany submit: `ok:true`, `proposalId` (`prop-<hash>`, deterministyczny dla doc + znormalizowanej propozycji), `summary` (linia na op + budżet), `warnings`. Pola tylko dla MG (`expect`, `opInfo`, `ops`, `normalized`, `plan`) NIE idą do modelu.
- MG / zapis: `pack.validate(doc, proposal, { profile, rank, deselect | only, expect, allowVitals, plan, skipPlan })` -> to samo + `normalized`, `ops` (ostateczna lista; replace przeliczony na ops), `opInfo` (per op: rodzaj, itemId, nazwa, zmiany, kaskada, `splitSwap`), `selection`, `expect` (odciski z podglądu), `summary`, `itemData` (szuflada przedmiotu).
- L3: gdy `pack.plan` jest funkcją (T6), wołane jako `plan(doc, { target, mode: "ops", ops, rationale, choiceNotes, from? }, { dryRun: true, fromValidate: true })`; błędy/ostrzeżenia planu dołączane. Gdy `opts.plan` to GOTOWY obiekt Plan (tak robi apply T6: `{ plan: p }`), jest tylko dołączany, nigdy wołany z powrotem. Strażnik rekursji per uuid dokumentu.

## Otwarte wybory (zachowanie tymczasowe)
- V1. Ścisłość „strukturalne zawsze twarde” (7.5.2) vs in-play: w in-play błąd strukturalny, który JUŻ jest na karcie (ten sam kod + nazwa), jest tolerowany (info `baseline.tolerated`); nowy blokuje. Inaczej żadna z 64 próbnych kart (Massive przy randze Global itd.) nie dałaby się edytować w in-play. W creation blokuje wszystko.
- V2. In-play: kody budżetu (`attr.over`, `attr.unspent`, `budget.range`) zamieniane na info `budget.delta` („wg zasad kreacji ta zmiana kosztuje N punktów”); wszystkie inne nowe błędy blokują („brak nowych błędów”). Podpis tolerancji = kod + nazwa/atrybut/ścieżka (bez parametrów liczbowych).
- V3. Pola wrażliwe (O25: karma, bieżące Health/Resolve) są w schemacie i przechodzą z ostrzeżeniem `field.sensitive` (walidator nie zna tekstu MG). `allowVitals: true` (opcja T6) wycisza ostrzeżenie. Pola pochodne (max), flagi, img itp.: nie ma ich w schemacie (L0) i projekcja też je odrzuca (`field.forbidden`).
- V4. `updateActor.set` ma postać strukturalną (`attributes`, `texts`, `reputation`, `resources`, `name`, `karma`, `health`, `resolve`), nie ścieżki `system.*` ze spec 6: schemat strict wymaga wyliczonych pól. Projekcja przyjmuje też ścieżki z kropką (dla wywołań po stronie MG), sprawdzane białą listą.
- V5. Jeden obiekt `set` dla updateItem i updateActor; dozwolone klucze zależą od rodzaju op i typu przedmiotu (moc: level/powerSource/note; boost/limit: power (przepięcie, z regułą folderu); talent/wada: note; gear: name/descriptionAppend/gear). Przepięcie boosta/limitu do mocy spoza jego folderu = `ref.power.mismatch`.
- V6. Przedmioty własne tylko gear/vehicleWeapon (10.3): `customItemData` buduje WYŁĄCZNIE name, opis jako tekst w `<p>` (escapowany), cost/restricted/singleUse, max. jedną automatyzację `rollAttack` (liczby; `attribute` domyślnie agility gdy maxRange > 0, inaczej fighting). `baseRef` ze spec 6 dla szuflady przedmiotu NIE jest w schemacie (byłby też w addItem.custom; tam służy `ref`). Do decyzji, czy dodać.
- V7. Limit `grants`: zapis nie ma pola na to; odczyt (heurystyka import.mjs) liczy limit jako „level”, gdy moc > Basic, inaczej „boost”. Gdy model poda inaczej: ostrzeżenie `grants.heuristic` (nie błąd).
- V8. Moc dzielona na poziomy: zmiana poziomu to jedna op `updateItem` z `opInfo.splitSwap { from, to, fromRef, toRef }`; zamianę dokumentu (ten sam `powerSource`, przepięcie boostów/limitów) robi zapis T6.
- V9. Moc bez źródła: superbohater zawsze błąd `link.source.missing`; NPC tylko wtedy, gdy ma jakiekolwiek źródło (NPC bez źródeł jest dozwolony, 7.4).
- V10. NPC (7.4): atrybuty 0..12 (`attr.range`), poziomy istniejące dla mocy (`power.level.none`; Monstrous dozwolony, jeśli moc go ma), linki, duplikaty talentów/wad, notatka wady (ostrzeżenie), „zagrożenie” vs ranga = info `npc.threat`. Brak limitu 2 wad dla NPC (spec nie wymienia).
- V11. Ranga: szuflada (`options.rank`) > flaga plus-ultra > Global; `proposal.rank` w replace różny od rangi szuflady = ostrzeżenie `rank.differs`, walidacja i tak wg rangi szuflady (O8).
- V12. Koszt na op = skumulowane projekcje (op k względem op k-1): zależny od kolejności (np. limit liczony przy boostcie dodanym później). Pola: `points` (zmiana budżetu), `slots`, `spent`.
- V13. Dwie konwersje replace -> ops: moja `replaceToOps` (proposal.mjs, używana przez walidację) i `toOps` T6 (replace.mjs, w toku). Docelowo jedna; walidacja może przejść na `toOps` T6, gdy będzie gotowe (ten sam kształt op).
- V14. Rozmiar narzędzi: oba narzędzia niosą cały schemat; po przeniesieniu opisów pól do `PROPOSAL_GUIDE` razem ~15k znaków JSON (~4,3k tokenów wg znaki/3,5; spec 9.2 szacował 2,5-3,5k dla WSZYSTKICH narzędzi). Alternatywa (do decyzji): jedno narzędzie `submit_proposal` z `dryRun: true` zamiast `check_proposal` (~-2k tokenów).
- V15. „Pola spoza zakresu polecenia MG” (L4, 7.1) nie są heurystyką: walidator nie widzi tekstu MG; zmienione pola aktora są w `summary`/`opInfo`, więc podgląd je pokazuje.
- V16. `profile.suggestInPlay` (info) przy profilu creation, trybie ops i karcie, która już nie przechodzi zasad kreacji.
